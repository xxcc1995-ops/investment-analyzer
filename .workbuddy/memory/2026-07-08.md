## 八大战法「已登录仍提示登录」根因修复（重要）
- **根因**：`cb_service.JISILU_CB_URL` 用的是旧接口 `cb_list/`，该接口已被集思录废弃（返回 HTTP 200 + 空 body），导致 `_fetch_jisilu_cb()` 永远拿不到数据 → 回落 AKShare → 触发「请登录集思录」误导提示。正确的接口是 **`cb_list_new/`**（页面 JS 中 `dataURL: '/data/cbnew/cb_list_new/'`）。
- **修复**：
  1. `JISILU_CB_URL` 改为 `cb_list_new/`。实测返回 317 只完整 JSON（含 year_left/ytm_rt/volume/turnover_rt 等 64 字段）。
  2. `_normalize_cb` 字段映射对齐 cb_list_new：`stock_pb`←`pb`、`redeem_price`←`real_force_redeem_price`、`force_redeem`←`redeem_dt`（已公告强赎债正确排除）。
  3. **成交额(turnover)公式修正**：cb_list_new 无 `amount` 字段，旧代码 `volume*price/10` 差 100 倍。改为 `volume*price/1000`（volume 单位=手，1手=10张=1000元，成交额万元=volume×10×price/10000）。
  4. 误导性提示修复：门控逻辑区分「未登录」vs「已登录但集思录取数失败」，后者不再说「请登录」。
- **验证**：grid 策略 data_source=jisilu、total=25（临期债 year_left 0.33~1.32年、turnover 451~1335万，数值合理）；ytm_defense/negative_premium/problem_bond=0 为筛选严格（非 bug，正收益债因 turnover=0 被流动性过滤）。
- 注意：网页版兜底 `_fetch_jisilu_cb_web` 仍因 `playwright` 未安装而 import 失败（Scrapling Fetcher 加载期即 import playwright），但主接口已恢复故不阻塞；如需启用网页版兜底需 `pip install playwright` + 下载 chromium。
- 重启后端方式（Git Bash）：先 `Stop-Process -Id <PID> -Force`（PowerShell）结束旧 uvicorn，再 nohup 启动；`taskkill /PID` 在 bash 下 `//PID` 参数会失效，用 PowerShell 更稳。

## 修复 start.vbs VBScript 编译错误（Unterminated string constant, 800A0409）

## 浏览器开了但后端没起的真凶：start 子命令的嵌套引号 bug（本次修复）
- **用户"双击完自动打开了"复探**：5180 与 8022 **均 NOT LISTENING**，且 `backend/start_backend.log`、`frontend/start_frontend.log` **均未生成** → 脚本跑到了最后开浏览器那行，但 `start` 拉起前后端的子进程**根本没启动**。

- **修复（bat 最佳实践）**：把 `cd /d` 移到 `start` **之前**（主进程用绝对路径 `cd /d "%ROOT%backend"`），`start` 的子 cmd 只跑**一条简单命令**（无 `&&`、无 `""` 转义）：`start "Invest-Backend" /min cmd /c "venv\Scripts\python.exe -m uvicorn app.main:app --reload --port %BACKEND_PORT% > start_backend.log 2>&1"`；前端同理 `cmd /c "node_modules\.bin\vite.cmd --port %FRONTEND_PORT% --host 127.0.0.1 > start_frontend.log 2>&1"`。日志路径变量 `%BE_LOG%/%FE_LOG%` 与 `type` 打印处仍一致（写到 backend/frontend 目录下的同名文件）。
- **验证（静态）**：start.bat non-ascii=0；两条 start 行均为单条简单命令、`&&`/`""` 转义已无；`BE_LOG`/`FE_LOG` 定义与 `type` 打印一致。

- **bat 引号纪律（固化经验）**：①`start "title" /min cmd /c "..."` 里的 `...` 必须是**单条简单命令**，绝不能写 `&&` 拼接或 `""` 转义路径；②需要切换目录时，在 `start` 之前的行用 `cd /d "绝对路径"` 完成；③路径含空格才需要引号，且只在 `cmd /c "..."` 这层内用单层 `"`。

## 最终解法：弃用 bat `start`，改用 PowerShell 启动器 `start.ps1`（彻底绕开不可靠的 start）
- **再双击一次仍失败（实锤）**：浏览器开、复探 host 8022/5180 仍 NOT LISTENING、backend/frontend 日志**仍未生成**；netstat 确认 8022/5180 均空闲（干净端口没被占），但进程没起。`start "" http://x`（直接拉浏览器）能开，而 `start "title" /min cmd /c "python..."`（经 cmd 包裹）起不来 —— 确定 **bat 的 `start` 在这套宿主环境无法可靠拉起经 `cmd /c` 包裹的后台进程**（与引号/`&&`/cd 写法无关，已逐一排除）。反复调 bat 是死路。
- **决策**：彻底弃用 bat `start`，改 **PowerShell 启动器 `start.ps1`**。后端 `Start-Process` 直接调 `backend\venv\Scripts\python.exe`（绝对路径 + `-WorkingDirectory backend`，**无 cmd 包裹**）；前端 `Start-Process` 直接调 `node node_modules\vite\bin\vite.js`（`-WorkingDirectory frontend`，**无 cmd 包裹**，`vite.js` 已确认存在可直启）。均 `-RedirectStandardOutput/-Error` 落盘、`-WindowStyle Hidden`；`netstat` 轮询就绪；`Start-Process` 开浏览器；末尾 `Read-Host` 让窗口停留显示结果。
- **`start.bat` 降级为入口**：仅自提权（`net session` 测权限→非管理员 `Start-Process powershell -ArgumentList '-ExecutionPolicy Bypass -File start.ps1' -Verb RunAs`）+ 管理员态 `powershell -ExecutionPolicy Bypass -File start.ps1` 委托。所有启动逻辑在 ps1。
- **验证（静态）**：start.bat non-ascii=0、委托 start.ps1、自提权 RunAs 就位；start.ps1 用直启 python/node 绝对路径、**无 `cmd /c`、无 bat `start`**。沙箱 PS 工具被策略拦无法跑 ParseFile，语法为标准形式、路径已确认，交宿主双击验证。
- **用户操作（本次·PowerShell 方案）**：双击 `start.bat` → 自提权→powershell 跑 start.ps1→直启后端8022/前端5180→开浏览器5180→窗口停留显示日志。双击后告诉我，我 curl host 8022 复探 `/api/relative-valuation/sectors` 变 200 即成功。若仍失败，powershell 窗口会显示未就绪错误及日志路径（backend\start_backend.log / .err），发我即可精准定位。**后备（若双击仍不行）**：在宿主管理员 PowerShell 粘贴两行 `Start-Process` 直启命令（同 ps1 逻辑），等效且可靠。
- **通用经验（可存 skill）**：Windows 上「双击 .bat 用 `start` 拉起 `cmd /c` 后台进程」在受限/虚拟化宿主环境可能静默失效（进程不起、无日志）。可靠替代：`start.bat` 仅做自提权入口，`-File` 委托 `start.ps1`，在 ps1 里用 `Start-Process` 直启可执行文件（`-WorkingDirectory` 指定目录、`-RedirectStandard*` 落盘），彻底避开 bat `start` 与 `cmd /c` 引号地狱。

## 二次强化 `start.ps1`（去 --reload + cmd 包装 + transcript）
- **现象（实锤）**：改用直启 python/node 的 ps1 后，前端 5180 能起（node 直启成功）、后端 8022 仍 NOT LISTENING，且 backend/frontend 日志文件**一个都没生成**（连 .err 都没有）。python.exe/vite.js 路径均确认存在。说明：`Start-Process` 直启后端那行**未真正拉起进程/未生成重定向文件**。
- **根因假设**：①`uvicorn --reload` 在 `Start-Process` 隐藏子进程里启动 reloader 子进程会失败（前端 node 无 reloader 故能起，后端有 reloader 故不能起 —— 与"前端能/后端不能"的现象吻合）；②PowerShell 的 `-RedirectStandardOutput/-Error` 在这套环境不可靠（进程未起时文件不创建）。
- **修复**：①后端启动**去掉 `--reload`**（改 `uvicorn app.main:app --port 8022 --no-use-colors`，静态启动可靠）；②改用 **cmd 包装**：ps1 动态生成 `backend_launch.cmd`/`frontend_launch.cmd`（内容为 `cd /d 绝对目录 && python/node ... > log 2>&1`），`Start-Process` 只启这个 .cmd；cmd 自己的 `>` 重定向**必定创建日志文件**，彻底绕开 PowerShell 重定向 bug；③加 `Start-Transcript -Path ps1_transcript.log -Append`，把 ps1 全过程（含 Wait-Port 的 ERROR、python 报错）记录到文件，下次能从沙箱读 `ps1_transcript.log` 精确定位。
- **静态验证**：start.ps1 non-ascii=0、`$PSScriptRoot` 就位、启动命令无 `--reload`、`backend_launch.cmd`/`frontend_launch.cmd` 包装就位、`Start-Transcript` 就位、cd/node 引号转义正确。
- **待用户操作（本次）**：再双击 `start.bat`。若后端起来，host 8022 复探 `/api/relative-valuation/sectors` 应变 200。无论成败，`ps1_transcript.log` + `start_backend.log` 这次必定生成，双击后我读这两个文件 + curl 8022 即可精确定位（不再黑盒）。
